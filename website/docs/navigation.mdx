# Navigation

**react-navigation** and **expo-router** both work, with no change to your app.

```bash
npm install @react-navigation/native @react-navigation/native-stack \
            react-native-screens react-native-safe-area-context
```

Screens render, `navigation.navigate` pushes, and a press on a `<Link>` routes.
Verified by running both on a desktop host and reading the mounted view tree.

## Screen stacking, and the one line it needs

Basalt implements react-native-screens' components, and a stack shows its top
screen and detaches what is under it. Whether your app reaches that code is the
library's decision rather than Basalt's.

```js
import {enableScreens} from 'react-native-screens';
enableScreens();
```

| | |
| --- | --- |
| **Windows** | works already, and needs no call. `Platform.OS` is `windows`, which react-native-screens has on its own list. |
| **macOS and Linux** | the call is a no-op today and becomes the switch when [software-mansion/react-native-screens#4779](https://github.com/software-mansion/react-native-screens/pull/4779) lands. Harmless to add now. |

Until then, a pushed screen leaves the one beneath it mounted on those two.
There is nothing to see: the top screen covers it at the same size. What it
costs is a subtree that is still measured and still reachable by a screen
reader.

:::note[Why Basalt cannot just turn it on]
```js
// react-native-screens/src/core.ts
export const isNativePlatformSupported =
  Platform.OS === 'ios' || Platform.OS === 'android' || Platform.OS === 'windows';
```

That const is what `Screen` checks, and it is not a list of platforms where
native screens could work. It is the list of platforms the library ships native
code for, which is why `macos` is absent: react-native-macos reports `macos`
too, and react-native-screens has no macOS implementation. Adding the name
would claim support that does not exist and would break those apps.

So the upstream change is an opt-in rather than a longer list: an app on a
platform that provides the components itself says so, and nothing else moves.
Basalt could instead patch the library through its Metro config, and does not,
because `metro-config.ts` argues that the library fallback "cannot be a list of
names", and owning a third-party module's internals for one library is the
worse problem.
:::

## What works

| | |
| --- | --- |
| `@react-navigation/native` with `native-stack` | screens render and navigate |
| expo-router | file routes under `app/`, `<Link>` routing, the stock entry point |
| `SafeAreaProvider`, `useSafeAreaInsets` | real insets, which are zero on a desktop |
| `initialWindowMetrics` | the window the app started with |

Insets are zero on every desktop, which is the correct answer rather than a
placeholder: a window has no notch and no home indicator. If a desktop ever
draws over its own content, a title bar on top of the client area for instance,
that is where a non-zero inset would come from.

## Headers

A header is a bar when it has something in it, and nothing when it does not.

`headerShown: false` removes it. A header with a title, a back button or
anything custom becomes a bar sized to its content plus a margin, with the body
of the screen moved down below it rather than hidden behind it.

:::warning[A plain string title draws nothing]
```jsx
// No header: the title goes to a toolbar this platform does not have.
<Stack.Screen name="Home" component={Home} options={{title: 'Home'}} />

// A header, because react-navigation renders a centred title as a view.
<Stack.Screen
  name="Home"
  component={Home}
  options={{title: 'Home', headerTitleAlign: 'center'}}
/>

// Also a header, and the way to control what is in it.
<Stack.Screen
  name="Home"
  component={Home}
  options={{headerTitle: () => <Text style={{fontWeight: '600'}}>Home</Text>}}
/>
```

react-navigation sends a left-aligned string straight to the native navigation
bar as a prop, and renders it as a `<Text>` only when it is centred or supplied
as a component. Basalt can lay out a view; it cannot draw a prop that no bar
exists to receive. Rather than reserve an empty strip for one, a header with no
content takes itself out of the layout entirely, so the default looks like no
header instead of a broken one.
:::

## What does not, yet

- **A covered screen stays mounted on macOS and Linux.** Pushing a second
  screen leaves the first in the view tree at full size, underneath. It looks
  right, because the top screen covers it, but both are measured and both reach
  accessibility. Windows does not have this, for the reason above.
- **Tabs are untested.** `TabsHost` and `TabsScreen` ship no desktop file, so
  the bundler falls back to their Android implementations and says so as it
  builds.

That one has a history worth recording, because the obvious fix is not the fix.
`RNSScreen` has an `activityState` prop and Basalt hides a screen whose
`activityState` is 0, which looks like the answer and is not: a native stack
never sets it to 0. react-native-screens throws `activityState cannot be
decreased in NativeStack`, because on iOS the navigation controller covers the
lower screen rather than the prop. Measured rather than assumed, every screen in
a pushed stack reports 2, the covered ones included.

So the stack does it instead. `RNSScreenStack` gives every screen below the
topmost opaque one `DisplayType::None` after layout, which all three hosts
already turn into a hidden widget, and a hidden widget is out of the
accessibility tree on each of them. A transparent modal covers nothing, so the
search for "topmost opaque" walks past one.

## Versions

expo-router needs the React Native its Expo SDK targets, which for SDK 57 is
**0.86.3**. Against 0.87 the bundle fails inside Expo's own Metro config
looking for a `react-native/rn-get-polyfills` that 0.87 no longer ships. That
is upstream of Basalt.

`@react-native/assets-registry` also has to resolve at the top level of
`node_modules`, at the version your React Native wants. expo-router ships PNGs
and cannot reach the copy nested inside `react-native`.
