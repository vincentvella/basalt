# Navigation

**react-navigation** and **expo-router** both work, with no change to your app.

```bash
npm install @react-navigation/native @react-navigation/native-stack \
            react-native-screens react-native-safe-area-context
```

Screens render, `navigation.navigate` pushes, and a press on a `<Link>` routes.
Verified by running both on a desktop host and reading the mounted view tree.

:::warning[Screen stacking works on Windows only, for now]
Basalt implements react-native-screens' components, and a stack correctly shows
its top screen and hides what is under it. Whether your app reaches that code is
the library's decision, not Basalt's:

```js
// react-native-screens/src/core.ts
export const isNativePlatformSupported =
  Platform.OS === 'ios' || Platform.OS === 'android' || Platform.OS === 'windows';
```

That is a const, and `Screen` renders its native component only when it is true.
Basalt's Windows host reports `windows`, so it is on the list and gets the
behaviour today. On `macos` and `linux` the library renders plain views instead,
`enableScreens()` does not change it, and every pushed screen stays mounted.

The fix is one line upstream, adding `'macos'` and `'linux'` to that list. Until
then the only visible consequence is the one below.
:::

## What works

| | |
| --- | --- |
| `@react-navigation/native` with `native-stack` | screens render and navigate |
| expo-router | file routes under `app/`, `<Link>` routing, the stock entry point |
| `SafeAreaProvider`, `useSafeAreaInsets` | real insets, which are zero on a desktop |
| `initialWindowMetrics` | the window the app started with |

Insets are zero on every desktop, which is the correct answer rather than a
placeholder: a window has no notch and no home indicator. If a desktop ever
draws over its own content, a title bar on top of the client area for instance,
that is where a non-zero inset would come from.

## What does not, yet

- **No header.** `RNSScreenStackHeaderConfig` mounts and takes no space, so a
  native stack has no title and no back button. Pass `headerShown: false` and
  draw your own.
- **A covered screen stays mounted on macOS and Linux.** Pushing a second
  screen leaves the first in the view tree at full size, underneath. It looks
  right, because the top screen covers it, but both are measured and both reach
  accessibility. Windows does not have this, for the reason above.
- **Tabs are untested.** `TabsHost` and `TabsScreen` ship no desktop file, so
  the bundler falls back to their Android implementations and says so as it
  builds.

That one has a history worth recording, because the obvious fix is not the fix.
`RNSScreen` has an `activityState` prop and Basalt hides a screen whose
`activityState` is 0, which looks like the answer and is not: a native stack
never sets it to 0. react-native-screens throws `activityState cannot be
decreased in NativeStack`, because on iOS the navigation controller covers the
lower screen rather than the prop. Measured rather than assumed, every screen in
a pushed stack reports 2, the covered ones included.

So the stack does it instead. `RNSScreenStack` gives every screen below the
topmost opaque one `DisplayType::None` after layout, which all three hosts
already turn into a hidden widget, and a hidden widget is out of the
accessibility tree on each of them. A transparent modal covers nothing, so the
search for "topmost opaque" walks past one.

## Versions

expo-router needs the React Native its Expo SDK targets, which for SDK 57 is
**0.86.3**. Against 0.87 the bundle fails inside Expo's own Metro config
looking for a `react-native/rn-get-polyfills` that 0.87 no longer ships. That
is upstream of Basalt.

`@react-native/assets-registry` also has to resolve at the top level of
`node_modules`, at the version your React Native wants. expo-router ships PNGs
and cannot reach the copy nested inside `react-native`.
